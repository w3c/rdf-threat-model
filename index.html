This document describes a threat model for RDF and SPARQL.

Introduction

This document describes a threat model for RDF. As you can probably tell, it is very much work-in-progress. In this document, we use the visual languaged proposed in [[[THREAT-MODELING-GUIDE]]] [[THREAT-MODELING-GUIDE]]. below present a global view of the threat model, which is explained step-by-step in the following sections.

Data Flow Description

describes a minimal data flow covering the different RDF specifications. A data owner owns a RDF graph (or dataset), and publishes it in a serialized form. This serialized form can be inspected directly by a developer, or consumed by an application used by an end user. That application needs to parse the serialized form back into a graph (or dataset), which the application then processes. One possible kind of processing is reasoning under one of the inference regimes described in [[[RDF12-SEMANTICS]]] [[RDF12-SEMANTICS]].

extends by considering that the application now uses data from two different providers (C1 and C3). The two corresponding graphs (or datasets) (S1 and S3) can be meaningfully integrated into the application's graph (or dataset), as they make use of the same shared vocabulary.

Dictionary

E1 Data Owner
An entity who publishes RDF data. See Section .
E2 End User
An entity who uses RDF data via an application. See Section .
E3 Developer
An entity who works with raw RDF data, usually in view of developing, debugging, or auditing an application. See Section .
C1 Data Provider, C3 Data Provider 2
An application or service allowing a data owner to publish RDF data. This could be for example a simple HTTP server serving static Turtle files, or a dedicated RDF triple store. This model leaves aside the means by which the data owner authors and curates the data. When this matters, the data owner is considered an end user of an application.
C2 Application
An application or service processing RDF data on behalf of an end user. Any application used to inspect, query, visualize, or edit the data, in conformance with the RDF data model [[RDF12-CONCEPTS]], is covered by this model. Simple text editors handling the serialized form of RDF data, without any awareness of the RDF data model, are not covered by this model; we consider them to be entirely trusted, hence transparent for the threat model (e.g. between P1 Serialize and E3 Developer in ).
S1 Graph, S2 Graph, S3 Graph
Data that conforms to the RDF data model [[RDF12-CONCEPTS]]. While we use the term "graph" for convenience, these components cover both [=RDF graphs=] and [=RDF datasets=].
P1 Serialize, P4 Serialize
The process of producing a representation of a graph (or dataset) into one of the concrete syntaxes, such as Turtle [[RDF12-TURTLE]] or RDF/XML [[RDF12-XML]].
P2 Parse
The process of producing a graph (or dataset) from a representation in one of the concrete syntaxes, such as Turtle [[RDF12-TURTLE]] or RDF/XML [[RDF12-XML]].
P3 Process
This process covers any processing that an application needs to perform on a graph (or dataset) to fulfill the needs of the end user. This can imply read and/or write operations on the underlying graph data.
